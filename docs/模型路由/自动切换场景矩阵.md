# 自动切换场景矩阵

## 文档目的

本文件先穷举当前路由和请求内重试的主要场景，区分“目前代码实际会怎样”与“产品还需要决定怎样”。它是产品方案评审的事实底稿，不代表目标行为已经确定，也不授权修改代码。

## 先看结论

当前代码的“自动切换”不是一个统一开关，而是多个机制叠加：首次选路、个人/社区来源回退、同请求其他渠道尝试、Responses 状态绑定恢复、故障渠道熔断分别由不同代码路径控制。因此同样的上游错误，在不同初始来源、请求状态、错误分类和请求策略下，可能得到不同结果。

当前代码中没有令牌级自动切换开关。`route_policy` 决定个人/社区来源边界和顺序；请求体 `provider` / `routing` 策略包含 `provider_scope`、`provider_order`、`retry_scope`；运行设置 `RetryTimes` 当前控制部分同请求其他渠道尝试。修复目标是让它只控制明确的上游传输故障，不能作为上游 HTTP 错误故障转移的总闸。

兼容性补充：历史 `route_policy=community_fallback` 会归一化为 `personal_first`，运行时不会作为独立策略处理。

## 场景维度

判断一次请求是否会换上游，至少要同时看以下维度。单独看 HTTP 状态码或渠道余额不足并不能得出结论。

| 维度 | 当前取值/状态 | 对结果的影响 |
| --- | --- | --- |
| 首次路由来源 | 指定渠道、明确选择的社区报价、个人连接、普通社区候选 | 指定渠道和社区报价基本固定；个人/社区自动路由可能有跨来源或同来源后备路径 |
| API Token 来源策略 | `personal_only`、`personal_first`、`community_only`、`community_first` | 限定来源范围或优先顺序；但已绑定 Responses 状态在部分情况下优先于当前策略 |
| 下游端点 | 文本、Responses、图像、音频、Realtime、视频/任务查询、其他代理端点 | 图像生成/编辑明确不走普通重试；视频查询通常通过任务绑定渠道；其余端点可能进入通用重试判断 |
| Responses 请求状态 | 无状态 ID、未知/过期 ID、单渠道绑定、个人/报价绑定、多渠道冲突 | 决定是否固定渠道、清理状态 ID、要求新会话或按普通候选重选 |
| 错误归属 | Router 本地校验/额度、客户端错误、上游瞬时错误、上游渠道硬故障、能力错误 | 决定 `shouldRetry` 与渠道熔断；这两个判断不是同一个开关 |
| 请求级选路策略 | `provider_scope`、`provider_order`、`retry_scope` | 初始候选与重试候选目前未完全使用同一套过滤逻辑 |
| 全局重试设置 | `RetryTimes=0` 或 `>0` | 仅对明确上游传输故障生效；`0` 关闭这类候选重试，`>0` 允许尝试其余候选。上游 HTTP 响应型故障转移不受它控制 |
| 候选池状态 | 模型/端点匹配、启用状态、权益/分组、可用额度、优先级、已失败集合 | 决定有无后备候选、后备顺序以及候选耗尽时的最终错误 |

请求级策略的当前取值如下。这里描述的是请求体 `provider` 或 `routing` 对象，不是 Token 来源策略：

| 字段 | 值 | 当前作用 |
| --- | --- | --- |
| `provider_scope.mode` | `any` / `allow_list` / `deny_list` | 对供应商候选做不过滤、白名单或黑名单过滤；初始社区选路会应用 |
| `provider_order` | 供应商顺序列表 | 初始候选排序，并可供 `ordered_providers` 重试判断使用 |
| `retry_scope` | `none` / `same_provider` / `ordered_providers` / `all_eligible` | 普通社区候选循环的范围；省略时默认 `same_provider` |
| `selection_method` | `priority` / `weighted_random` | 候选选择方式；当前只接受这两种值 |

这些字段当前不是全局统一约束：显式指定渠道、Responses 状态固定、跨个人/社区来源回退和普通社区候选重试并未全部经过同一筛选函数。

还要区分两种“自动走到另一来源”：首次请求选路时，`personal_first` / `community_first` 会按来源策略在首选来源不可用时尝试下一来源；上游已被实际调用并明确失败后，才是本轮要评审的故障转移。Token 开关是否只控制后者、不改变首次选路的既有来源顺序，需要在目标方案中明确。

## 上游调用前失败

以下失败发生在上游模型调用之前。它们不能通过改用另一个上游解决，因而不应被描述成“渠道自动切换失败”。

| 场景 | 当前结果 | 是否会尝试其他上游 |
| --- | --- | --- |
| API Token 缺失、无效、禁用、过期或请求模型不在 Token 授权范围 | 鉴权阶段拒绝请求 | 否 |
| 请求体路由策略格式错误，或同时声明互斥的 `provider` 与 `routing` | `400` 拒绝请求 | 否 |
| 用户当前没有该模型的权益/分组授权 | 权益解析阶段拒绝请求 | 否；`community_first` 且端点支持个人连接时，可尝试已授权的个人来源 |
| 普通候选没有符合模型、端点、启用状态和来源过滤的渠道 | 分发阶段返回无可用渠道 | 否；`community_first` 可按其独立来源分支尝试个人连接 |
| 指定渠道无效或已禁用 | 分发阶段返回错误 | 否 |
| 社区渠道已选中，但 Token 金额额度不足 | 上游转发前返回本地额度错误 | 否 |
| 请求 JSON/参数不合法、端点策略拒绝或模型计费配置不完整 | relay 前置校验返回错误 | 否 |
| 社区报价预算超出用户余额或报价结算配置不可用 | 报价转发前拒绝请求 | 否 |

这里的“上游渠道余额不足”是供应商账户的额度/余额问题，和上表里的 Router 用户余额、Token 额度不是一类错误。前者可能触发离开渠道；后两者是本地付费资格，不应靠换渠道绕过。

## 首次选路场景

| 首次场景 | 当前行为 | 初次来源不可用时 |
| --- | --- | --- |
| 有 `SpecificChannelId` | 直接加载指定渠道；不进入普通分组候选选择 | 渠道无效/禁用时直接报错；后续上游错误不做通用请求内重试 |
| 用户明确选择社区报价 | 选定报价作为固定来源，不参与普通分组候选随机选择 | 选定报价不可用时在选路阶段报错；上游失败时普通社区候选循环被关闭 |
| `personal_only` 且有匹配个人连接 | 从用户个人连接中选一个 | 无匹配连接或凭据读取失败时返回个人连接不可用，不回退供给渠道 |
| `personal_only` 且无匹配个人连接 | 不选社区渠道 | 返回无可用个人连接 |
| `personal_first` 且未配置社区报价路由、有匹配个人连接 | 首先选个人连接；不预先要求社区权益 | 如果个人上游发生可重试错误，代码会尝试选一个符合请求策略的社区候选；该跨来源路径不要求 `RetryTimes>0`，也不被 `retry_scope=none` 阻断 |
| `personal_first` 且无个人连接 | 按用户权益选择普通社区候选 | 没有社区报价路由且没有社区权益/候选时返回无可用渠道 |
| `community_only` | 只选择普通社区候选，不使用个人连接 | 没有候选时返回无可用渠道；请求内社区渠道重试仍受一般错误/重试门槛约束 |
| `community_first` | 有明确社区报价路由时先使用该报价；否则先使用普通社区候选 | 普通社区首次选路失败时，可在符合端点条件时回退个人连接；社区上游失败后也存在个人连接后备路径 |
| 端点不支持个人连接 | 路由忽略个人连接，只按社区/指定来源处理 | 不存在可用社区候选时失败 |

`personal_first` / `community_first` 是来源顺序，不等于单一渠道内的重试规则。当前只要不是 `personal_only`，已配置的社区报价路由会先于个人连接选择；社区报价上游失败后，普通社区候选循环虽被关闭，`community_first` 的个人后备分支仍可能继续尝试。这与“明确报价固定”的注释/产品语义存在差异，见后面的已确认差异。

## Responses 状态场景

Router 对响应 ID 和 item ID 保存的是短期“ID -> 渠道”绑定，不保存或迁移上游会话内容。绑定默认 6 小时；配置 Redis 时使用 Redis，否则使用进程内存。

| 请求携带的状态 | 绑定情况 | 当前路由/失败行为 |
| --- | --- | --- |
| 无 `previous_response_id`、无已识别 item ID | 无绑定 | 按普通来源策略首次选路；初次 Responses 调用失败时按通用错误规则判断是否重试 |
| 有 `function_call_output`，但无 `previous_response_id` 和 item ID | 无绑定 | 请求被标为 stateful，但重试侧没有可绑定 ID，因此仍可能按通用规则重试 |
| 带 `previous_response_id` 或 item ID | 找不到绑定、绑定过期或 Redis 未命中 | 按普通来源策略选路，但状态 ID 原样保留；请求被识别为 pinned 时不会做请求内重试，上游可能以状态/ID 不兼容错误拒绝 |
| 仅有 input item ID，无 `previous_response_id`，且无 `function_call_output` | item ID 有绑定 | 分发器可能固定到绑定渠道，但重试侧不会将请求判为 pinned；上游失败时仍可能按普通规则跨渠道重试 |
| 状态 ID | 绑定到仍启用且仍符合模型/端点条件的普通社区渠道 | 优先固定到该渠道；recognized pinned Responses 上游失败时不做请求内切换 |
| 状态 ID | 绑定到已禁用、已失去当前模型/端点资格的普通社区渠道 | 清除本次请求的 `previous_response_id` / item ID，再重新选路；这只是去除旧引用，不是会话迁移 |
| 状态 ID | 绑定到已不可用的个人连接 | 返回 `409 Conflict`，要求新建会话 |
| 状态 ID | 绑定到已不可用的明确社区报价 | 返回 `409 Conflict`，要求新建会话 |
| 同一请求内的多个状态 ID | 分别绑定到不同渠道 | 清除本次请求中的状态 ID，再重新选路；不会合并不同上游上下文 |
| 状态 ID | 绑定到仍可用渠道，但本次上游调用失败 | 对被识别为 pinned 的会话，不因一般重试配置切换；客户端得到最终上游错误 |
| 上游明确报 item ID 前缀不兼容 400 | 绑定/来源均不改变 | 归一化为 `state_incompatible`，提示新建会话；不会自动禁用整条渠道 |

重要边界：`previous_response_id` 或 item ID 本身不能恢复上游保存的历史。当前实现遇到普通社区绑定失效或跨渠道 ID 冲突时会移除 ID 后重放请求体；若请求体只有增量内容，调用虽可能继续，却不能保证原会话上下文完整。

状态 pin 当前先于普通来源策略/供应商过滤处理。例如用户在会话建立后把 Token 来源策略从 `personal_first` 改为 `community_only`，若旧 ID 仍绑定个人连接，Router 当前仍可能优先恢复该个人连接；普通社区 pin 也可能在没有重新应用 `provider_scope` 的情况下继续使用。这是需要决定的策略冲突，不应假设已绑定会话必然服从最新 Token 边界。

另有一处状态识别差异：分发器会读取 Responses input item ID 并可能据此固定渠道，但重试侧是否认定为 pinned，还依赖 `ResponsesStatefulRequest` 标记。该标记当前由 `previous_response_id` 或 `function_call_output` 设置；“只有 item ID、没有前两者”的请求可能出现分发固定而重试判断未固定的情况，需作为产品/实现修复项评审。

## 上游失败场景

当前代码中，`shouldRetry` 判断错误是否可继续尝试，`shouldRetryRemainingCandidates` 再结合 `RetryTimes` 决定是否启动普通候选循环。按本次修复目标，只有明确上游传输错误由 `RetryTimes` 门控；已收到的上游 HTTP 错误应直接按候选故障转移规则处理。个人/社区跨来源分支也应遵循相同的传输错误门控。

术语需要区分：当前代码把“尝试另一个候选上游”也叫请求内 retry；产品上应分为故障转移与网络重试。当前传输错误码按 `do_request_failed`、`read_response_body_failed`、`upstream_transport_goaway` 分类。客户端取消、下游写响应失败、响应已开始输出时不应重放请求。

| 失败类别 | 当前 `shouldRetry` | `RetryTimes=0` 时普通候选循环 | 其他当前动作 |
| --- | --- | --- | --- |
| 客户端取消/断开 | 识别为 client abort 后终止，不继续尝试 | 否 | 标记 client-aborted；不按普通上游失败归档 |
| Router 本地用户余额、Token 额度、分组日额度不足 | 否 | 否 | 保留本地策略错误；换上游不能解决 |
| 用户请求格式/参数错误，普通 `400` | 否 | 否 | 保留错误；Responses 特定状态 ID 不兼容也归到此类 |
| 用户输入错误 `422` 或内容安全拒绝 | 否 | 否 | 不把用户输入/安全拒绝当成渠道故障 |
| 普通上游 `401` / 鉴权失效 | 通常是 | 是，识别为渠道硬故障 | 可能禁用渠道或模型端点，最终错误再归一化 |
| 上游额度/余额不足或 `402` | 是 | 是，不由 `RetryTimes` 控制 | 可能禁用该渠道的模型端点并排入恢复测试 |
| 上游 `429` 响应 | 是 | 是，不由 `RetryTimes` 控制 | 按候选故障转移；候选耗尽后通常归一化为 `503` |
| 上游 HTTP `5xx` 响应 | 是 | 是，不由 `RetryTimes` 控制 | 按候选故障转移；不能与传输层失败混为一类 |
| 上游传输错误 (`do_request_failed`、`read_response_body_failed`、`upstream_transport_goaway`) | 是 | 仅 `RetryTimes>0` | 启用时尝试其他候选；客户端取消、下游写响应失败或响应已开始输出时不重放 |
| 模型/端点能力错误 | 是（能力错误分类优先于一般 `400` 判断） | 是，不由 `RetryTimes` 控制 | 可能禁用 `channel + model` 或 `channel + model + endpoint` 并安排恢复测试 |
| 其他非 `2xx` | 通常是，除 `400` 外的未特殊排除状态码 | 是，不由 `RetryTimes` 控制 | 候选耗尽后按最后错误分类决定是否归一化 |
| 图像生成/编辑失败 | 普通重试被显式禁止 | 否 | 不走通用请求内渠道重试 |
| 有状态 Responses 上游失败 | 被识别为 pinned 时否 | 否 | 维持固定来源；未识别 pinned 的状态形态按普通请求逻辑处理 |
| 指定渠道请求失败 | 否 | 否 | 明确渠道语义优先，不自动换渠道 |

错误状态码只是门槛的一部分：同为 `403`，本地用户额度不足不会重试，上游账号权限/额度问题可能重试；同为 `400`，普通参数错误不重试，但被分类为模型/端点能力错误时可能重试。

## 候选选择和耗尽场景

进入普通社区候选循环后，Router 排除本次请求已失败的渠道，并按分组、模型、请求端点选择剩余候选；当前按优先级逐层处理，同优先级内随机选择。候选池被耗尽或选择失败后，不再有可尝试社区渠道，最终使用最后一次失败信息生成响应。

| 候选情况 | 当前结果 |
| --- | --- |
| 没有其他模型/端点匹配候选 | 当前失败结束，不会创造新来源 |
| 还有同优先级候选 | 先在该优先级剩余候选中选择 |
| 当前优先级候选耗尽但较低优先级仍有候选 | 继续尝试较低优先级 |
| 候选已在本请求失败 | 本请求后续候选选择会排除该渠道 |
| 个人首次失败，社区候选成功 | 请求成功并记录回退；社区计费/额度规则生效 |
| 社区首次失败，`community_first` 个人后备成功 | 请求成功；该后备尝试不依赖普通 `RetryTimes` 候选循环 |
| 全部候选失败 | 返回最后错误；瞬时错误、上游额度/能力错误通常归一化为 `503`，其他错误保留相应语义 |
| 重试候选不符合 `retry_scope` | 跳过该候选，继续检查剩余候选；全部过滤后视为无后备候选 |

普通重试循环当前不总是复用首次选路时应用的完整来源筛选。下一节列出具体差异，不能仅依据首次选路的候选日志推断所有重试都遵守同一候选集合。

## 当前策略/实现差异

以下是从代码路径直接核对出的差异，不是目标方案；需要先决定预期规则，再讨论实现。

| 项目 | 当前实际情况 | 需要评审的问题 |
| --- | --- | --- |
| `RetryTimes` 的含义 | 修复后 `>0` 只开启明确上游传输故障后的其他候选尝试；`0` 不影响 HTTP 响应型错误的故障转移 | 保持现有二态管理配置，不把它解释为自动切换开关或数值次数上限 |
| 个人/社区跨来源回退 | `personal_first` 个人连接失败后可直接尝试社区；`community_first` 社区失败后可尝试个人；这两条路径可绕过一般 `RetryTimes` 门槛。已配置的社区报价路由当前也会在 `personal_first` 下先于个人连接选中 | 自动切换令牌开关是否统一控制跨来源与同来源回退？来源顺序本身是否应继续允许首次来源不可用时换到下一来源？明确选定的报价是否应完全固定？ |
| `retry_scope=none` | 它关闭普通社区候选循环，但个人/社区跨来源的独立分支并未都检查它 | `none` 是否应成为本次请求的绝对“不再尝试任何上游”指令？ |
| `provider_scope` | 初始普通社区选路和部分个人到社区选择应用过滤；普通重试候选循环及 Responses 状态固定路径未始终重用该过滤 | `provider_scope` 是否必须限制每一次重试和已绑定会话？状态连续性与当前来源权限冲突时谁优先？ |
| 明确社区报价 | 普通候选循环关闭，但 `community_first` 失败后的个人连接后备分支仍需核对是否会触发 | 用户明确选定报价后，是否绝不允许任何其他来源接管本请求？ |
| Responses 状态恢复 | 普通社区状态失效/ID 冲突会移除状态 ID 后重选，不检查输入是否含完整历史 | 只有完整可重放历史时是否允许自动恢复？增量状态是否应该直接给稳定错误码并要求新建会话？ |
| Responses item ID 判断 | 分发绑定识别和重试侧 pinned 判断使用的状态条件不完全相同 | 所有会影响会话身份的 item ID 是否都应抑制跨上游重试？ |
| 非文本端点 | 图像生成/编辑显式不重试；其他未显式排除的端点可能使用通用重试判断，视频查询等可能另有指定渠道 | 哪些端点可在请求未完成前换上游，哪些任务/会话端点必须固定来源？ |
| 失败后重复执行风险 | 当前候选切换按错误分类和 HTTP 状态重放同一用户请求；代码没有统一的“上游是否可能已接收请求”策略 | 明确网络错误的分类应如何区分请求发送前失败与发送后结果未知？对于发送后超时、流式中断或工具调用，是否仅在有幂等保障时允许重放？ |

## 评审建议顺序

当前先不要求决定 Token 字段、默认值或 UI。请先评审以下事实底稿和故障分类边界：

1. 上面的现状分类是否覆盖你希望“自动切换”处理的全部请求来源和状态。
2. 产品语义区分“上游响应型故障后的候选故障转移”和“明确上游传输故障后的候选重试”；后者由 `RetryTimes` 控制，前者不受它影响。
3. 哪些代码事实与产品预期不符，尤其是 `provider_scope`、`retry_scope=none`、明确社区报价、Responses 状态恢复这几项。
4. 请指出要优先细化的具体场景。建议从“Responses 会话已绑定个人连接，随后个人上游额度不足”开始；网络错误分类已先限定为对应的上游传输错误码，后续还需确认请求发送后超时、结果未知时是否允许重放。

上述事项确认后，再把目标行为填入逐场景决策表，提交下一轮文档评审。评审通过前不改代码。
