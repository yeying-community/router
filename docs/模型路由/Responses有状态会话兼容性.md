# Responses 有状态会话兼容性

## 适用范围

本文说明 Codex 等客户端调用 `/v1/responses` 时，为什么不能在不同上游账号之间任意切换，以及遇到历史 item ID 不兼容时的处理方式。

当前全量路由与失败场景索引见[自动切换场景矩阵](自动切换场景矩阵.md)。本文中“当前实现”和“目标语义”应分开阅读。

## 问题表现

上游可能返回类似错误：

```text
Invalid 'input .id': 'fc_...'. Expected an ID that begins with 'ctc'.
```

其中 `fc_...` 通常是客户端历史中的 `function_call` item ID，`ctc...` 是某些上游会话系统要求的本地 item ID 前缀。

## 根因

Responses 请求可能携带以下状态：

- `previous_response_id`
- `function_call`
- `function_call_output`
- 历史 `input` item ID

这些状态不一定能被另一个上游账号或会话池识别。典型链路是：

1. Codex 会话先从上游 A 获得 `fc_...` item。
2. 上游 A 暂时不可用，Router 选择上游 B。
3. Codex 继续发送原会话历史。
4. 上游 B 只接受自己的 `ctc...` item，于是返回 400。

item ID 不能通过字符串替换解决，因为 ID 同时对应上游保存的会话状态。

## Router 行为

本节描述当前实现，后面的目标语义仍待产品评审。

Router 会按 Response ID 和 Responses item ID 查找原渠道。当前处理分为以下情况：

1. 请求中的状态 ID 分别绑定到多个渠道时，Router 会移除本次请求中的 `previous_response_id` 和 item ID，再重新选路。
2. 状态绑定到普通社区渠道，但该渠道已禁用、不再符合路由条件或不可用时，Router 会移除本次请求中的状态 ID，并重新选择当前可用渠道。
3. 状态绑定到个人供应商连接或用户明确选择的社区报价，而该来源不可用时，Router 返回 `409 Conflict`，提示用户重新开始会话。
4. 状态绑定的渠道仍可路由，但本次上游调用失败时，当前请求不会因普通重试策略而切换渠道。

移除状态 ID 只会让本次请求不再依赖旧上游的会话标识，不会把旧上游保存的会话内容迁移到新上游。若请求只带增量输入和 `previous_response_id`，新上游无法据此恢复完整上下文。

对于上游明确返回 item ID 前缀不兼容的 400，Router 会归一化为：

```json
{
  "error": {
    "type": "state_incompatible_error",
    "code": "state_incompatible",
    "message": "当前 Responses 会话与所选上游不兼容，请新建会话后重试"
  }
}
```

这不是渠道余额不足，也不会因此全局禁用渠道或模型端点。

## 自动回退目标语义（待评审）

自动切换由 API Token 上的开关控制，建议默认开启。这里的切换指首次上游明确无法承载请求后改选其他合规候选，不受旧 `RetryTimes` 的 0/非 0 语义控制；只有明确的网络层故障进入独立的重试机制。开启切换不代表会话状态可以跨上游迁移，也不保证候选一定可用。Token 来源策略、用户权益、分组授权、个人模型路由策略和请求 `provider_scope` 共同限制候选范围；用户明确选择的单个社区报价仍保持固定。完整规则见[自用渠道路由方案](个人供应商路由方案.md#令牌级自动回退待评审)及[自动切换场景矩阵](自动切换场景矩阵.md)。

有状态请求必须区分两种请求形态：

1. 请求携带足以重放会话的完整历史输入，且失败能确定属于可切换的上游故障时，Router 可以去掉旧上游的 `previous_response_id` 和 item ID，在符合策略的新上游开启新会话并重放请求。
2. 请求只携带 `previous_response_id` 或依赖旧上游的 item ID 与增量输入时，Router 无法从这些 ID 还原历史内容。自动转发到新上游会丢失上下文，可能令工具调用和回答语义改变。

产品建议：不要静默删除状态 ID 后把增量请求当成完整续接。若无法确认请求包含可重放的完整历史，应返回清楚说明上游已不可用、会话上下文无法恢复并需要新建会话的错误。此时可以识别和记录回退原因，但不能承诺本次请求自动恢复成功。

Router 不应为了让状态请求看起来可自动回退而默认保存用户完整对话历史。若要托管对话以支持会话重建，需另行评审数据保留和删除、用户告知、工具副作用以及跨供应商兼容。

待评审点：

1. 是否接受上述边界：完整历史可自动重放；只有上游状态 ID 的增量请求明确报错，不静默丢失上下文。
2. 是否需要在错误响应中提供稳定错误码，供 Codex 等客户端提示用户新建会话。

## 状态会话隔离

Router 会为上游返回的 Response ID 和 Responses item ID 建立短期渠道绑定，默认保存 6 小时；启用 Redis 时使用 Redis 共享绑定，未启用 Redis 时使用当前进程内存。

后续请求携带 `previous_response_id` 或历史 item `id` 时：

1. 优先查找原渠道。
2. 原渠道仍可承载当前模型和端点时，固定使用原渠道，不参与普通优先级随机选择。
3. 如果同一请求中的状态 ID 分别绑定到多个渠道，Router 会移除本次请求中的状态 ID，并重新选路；这不会合并或迁移原渠道保存的会话内容。
4. 没有可识别绑定的旧历史请求仍按普通规则选择渠道，但一旦上游返回 ID 前缀不兼容，客户端应新建会话。

绑定的是渠道级状态，不代表不同渠道之间可以共享上游会话；渠道内如果还有多个上游账号，会话池仍应由渠道供应商保证一致性。

## 排查和运维建议

1. 用户端新建 Codex 会话，不要继续重放已经产生不兼容 ID 的历史会话。
2. 尽量让一个 Responses 会话固定使用同一渠道和同一上游账号池。
3. 看到 `state_incompatible` 时，优先检查近期是否发生渠道切换、上游账号切换或上游会话重置。
4. 不要把 `fc_` 直接改成 `ctc`，也不要仅凭这个错误自动摘除整个渠道。

## 后续演进

若要实现跨上游的无损会话迁移，需要完整的会话重建、Response/item ID 映射和工具调用副作用治理。仅修改请求中的 ID 前缀，或单纯移除旧 ID 后转发，都不能保证会话语义不变。
